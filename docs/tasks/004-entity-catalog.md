## Критерии готовности

- Переименование и изменение aliases учитываются без перезапуска HA.
- После отключения exposure сущность исчезает из кандидатов.
- Одинаковые имена разных сущностей сохраняют неоднозначность.
- Проверены сущности без registry entry, отсутствующее состояние и удаление сущности; политика для unavailable документирована.
- Изменение обычного состояния без изменения имени не вызывает дорогостоящую полную перестройку словаря.

## Реализация и политика

Каталог хранится в `entry.runtime_data`. `catalog.snapshot` содержит неизменяемые записи и индекс `by_name`; одинаковое имя сохраняет всех кандидатов. Исходные aliases сохраняют написание, но одна сущность не дублируется в одном ключе индекса из-за разного регистра aliases.

Используются штатные `intent.async_get_entity_aliases`, `async_should_expose` и exposure listener. Registry aliases с `COMPUTED_NAME` разрешаются через HA; явный пустой список не заменяется state-именем. Без registry entry имя берётся из state. Без state запись исключается; `unknown` и `unavailable` сохраняются. Если registry удалён, но state ещё существует, применяется та же политика legacy-сущности с повторной проверкой exposure.

Area сущности имеет приоритет над effective area устройства, включая наследование от родительского устройства. Комнаты используются только как контекст, не как самостоятельные объекты нормализации. Подробности — в [архитектуре](../architecture.md).

## Проверки

Полный набор: `uv run --group integration pytest -q` — **48 passed**. Новые проверки используют реальные entity/device/area registries и exposure API HA, без подмены правил exposure. Проверены aliases и вычисленные имена, коллизии, запрет exposure и настройки новых сущностей, добавление/переименование/удаление, изменения state-friendly-name, отсутствие перестройки на обычном state update, атомарность снимка, комната дочернего устройства, cleanup и rollback setup, включая отмену. При ошибке обновления каталог очищается вместо использования устаревших кандидатов.

В пользовательском HA каталог пока отдельно не проверялся. На команды он не влияет до подключения нормализации в 005; новые runtime-зависимости не добавлены.
