# Архитектура и границы интеграции

## Решение

Реализовать `ConversationEntity` домена `morpholizer`, которую пользователь выбирает агентом Assist. Существующий llamacpp conversation entity выбирается в настройках Morpholizer; данные и credentials LLM остаются в исходной интеграции.

Реализованы маршрутизатор локальных интентов с fallback, каталог имён/aliases доступных Assist сущностей и морфологическая нормализация названий. После них доступен opt-in fuzzy matching (по умолчанию выключен): bounded Levenshtein-поиск, порог 90/отрыв 8, защита предыдущих совпадений и отказ при неоднозначности. Лимиты и синтетические метрики описаны в [006](tasks/006-fuzzy-matching.md); реальные STT и пользовательский HA ещё не проверены. Интеграция объявляет `CONTROL`, но не streaming.

Внешняя опция предпочтения локальной обработки выключена: последовательность «нормализация → локальный этап → LLM» выполняет Morpholizer. Для локального этапа используется `conversation.async_handle_intents(hass, user_input, chat_log, intent_filter=None)`, а не обычный ответ агента HA с разбором текста ошибки.

## Политика маршрутизации (задача 003)

- Только `None` из локального API разрешает однократный fallback. В HA это отсутствие строгого совпадения или ошибка сопоставления. Любой `IntentResponse`, включая ошибку выполнения, окончателен: повтор через LLM запрещён.
- Исключение локального обработчика возвращает безопасную ошибку без fallback: действие могло уже частично выполниться. Исключение fallback также не приводит к повтору. Текст исключений и пользовательского запроса не включается в обычные логи.
- Локальный ответ записывается в общий chat log. При делегировании используются ID активного chat log и неизменённые context, language, device/satellite ID, extra system prompt. Результат fallback возвращается без подмены полей.
- Проверка доступности fallback выполняется только после локального промаха: самостоятельные локальные команды работают при недоступном LLM.
- `ConversationResult.continue_conversation=True` закрепляет следующую реплику за тем же fallback. Это поле результата, а не наличие `?` в тексте. Состояние изолировано по сессиям, потребляется перед обработкой следующей реплики и удаляется при cleanup сессии или выгрузке entity. Отмена запроса распространяется вызывающему коду и не инициирует повтор.

### Отличие от штатного фильтра CONTROL

В HA 2026.11.1 `assist_pipeline/default_pipeline.py` передаёт фильтр для агентов с `CONTROL`. Predicate возвращает `True` для `HassGetState` и `HassMediaSearchAndPlay`, а `DefaultAgent.async_handle_intents` **исключает** такие совпадения из локальной обработки. Morpholizer намеренно использует `intent_filter=None`: все штатные интенты должны сначала обрабатываться локально, включая запросы состояния и медиапоиск. Проверки exposed entities и контекст текущего пользователя остаются штатными. Это осознанное отличие, а не точное копирование чекбокса Assist.

## Проверенные исходники целевой версии

При создании каркаса проверены исходники **тега 2026.11.1**, а не только ветка разработки:

- [Python и зависимости HA](https://github.com/home-assistant/core/blob/2026.11.1/pyproject.toml): `requires-python >=3.14.2`.
- [ConversationEntity](https://github.com/home-assistant/core/blob/2026.11.1/homeassistant/components/conversation/entity.py): `_async_handle_message(user_input, chat_log)` и supported languages.
- [Делегирование](https://github.com/home-assistant/core/blob/2026.11.1/homeassistant/components/conversation/agent_manager.py): `async_get_agent` и `async_converse`, включая text/context/language/conversation ID/device ID/satellite ID/extra system prompt.
- [Локальный API](https://github.com/home-assistant/core/blob/2026.11.1/homeassistant/components/conversation/__init__.py) и [DefaultAgent](https://github.com/home-assistant/core/blob/2026.11.1/homeassistant/components/conversation/default_agent.py): строгая обработка exposed entities, семантика `None` и исключающего фильтра.
- [Штатный pipeline](https://github.com/home-assistant/core/blob/2026.11.1/homeassistant/components/assist_pipeline/default_pipeline.py): локальные ответы, фильтр CONTROL и продолжение диалога.
- [ChatSession](https://github.com/home-assistant/core/blob/2026.11.1/homeassistant/helpers/chat_session.py): проверка владельца контекста, cleanup неактивных сессий (таймаут 5 минут).

`tests/test_local_intents.py` проверяет реальный русский recognizer, `DefaultAgent`, локальный API и `OnOffIntentHandler` через Morpholizer. Команда «включи кухонный свет» вызывает тестовый сервис ровно один раз и меняет state; ошибка сервиса не вызывает fallback; нераспознанная фраза вызывает его один раз. Использованы настоящий `ExposedEntities` и облегчённые registry-объекты. Полный HA bootstrap и физическое устройство не участвуют.

`tests/test_routing.py` проверяет изоляцию одновременных сессий, явный follow-up и его завершение, cleanup, отмену, передачу текста и контекста, терминальные ошибки и историю return-only агентов. При ошибке обработчика незавершённые tool calls закрываются через `ChatLog.async_add_error` с безопасным сообщением, без исходного текста исключения.

Чтение исходников не является runtime-проверкой. Дополнительно выполнен smoke-эксперимент в установленном HA 2026.11.1 с тестовым `ConversationEntity`: настоящий `async_converse` → Morpholizer → тестовый агент, новый conversation ID и две последовательные реплики. В этом сценарии ID сохраняется и история не содержит дубликатов user/assistant. Автоматическая запись состояний entity и доступ к registry подменены; полноценный запуск интеграции в пользовательском HA не выполнен. Эксперимент закреплён в `tests/test_ha_runtime.py` вместе с проверками делегирования и жизненного цикла.

После установки `59fbb03` пользователь подтвердил работу предложенных сценариев маршрутизации в своём HA («Все ок»). Точный репозиторий и версия установленной llamacpp-интеграции ещё не зафиксированы; детальная проверка tool history и streaming остаётся частью задачи 001. Streaming в задаче 003 намеренно не включён.

## Контракты

- Одна config entry Morpholizer; fallback выбирается среди существующих conversation entities, исключая собственные сущности Morpholizer.
- Настройки можно изменить через options flow.
- При невозможности делегирования не переключаться неявно на штатный агент HA и не повторять команду.
- Сохранять идентичность пользователя и метаданные запроса при делегировании; это не должно расширять права или exposure.
- Не добавлять второй assistant response поверх результата агента без проверки того, что он уже записал в chat log.
- Никаких credentials LLM в конфигурации Morpholizer.
- Не писать полный текст запросов в обычный лог.

## Каталог сущностей (задача 004)

`EntityCatalog` создаётся при setup config entry, до conversation-платформы, и хранится в `entry.runtime_data`. При неуспешном setup (включая отмену) подписки снимаются; при неуспешном unload платформы каталог остаётся рабочим. Успешный unload снимает подписки и отменяет отложенное обновление.

`catalog.snapshot` — неизменяемый снимок: tuple `CatalogEntry` и read-only `by_name`, где один ключ соответствует tuple всех кандидатов. Запись содержит entity ID, исходные имена/aliases, домен, area ID и имя комнаты. Ключи объединяют пробелы и регистр (`casefold`), без морфологии или fuzzy matching. Одинаковые имена не разрешаются произвольным выбором первой сущности.

Имена получаются через тот же `intent.async_get_entity_aliases`, что использует штатный агент HA 2026.11.1. С registry entry действуют именно registry aliases: `COMPUTED_NAME` разрешается в полное имя, пустой список aliases не заменяется автоматически state-friendly-name. Без registry entry используется `state.name`. Пустые имена исключаются. Комната берётся с entity entry, затем через effective area устройства с учётом parent device.

Каталог включает только текущие states, прошедшие `async_should_expose(hass, "conversation", entity_id)`. Без состояния запись исключается; `unknown`/`unavailable` сами по себе не исключают имя, как и в штатном агенте: недоступность устройства должна дать локальную ошибку, а не потерю имени и fallback. Hidden/disabled не используются как независимая замена exposure: явное решение пользователя остаётся за штатным API. Каталог не является отдельным механизмом авторизации.

Подписки: entity/device/area registry events, `state_changed` и публичный exposure listener. Обычные изменения значения state без смены имени не перестраивают каталог. Серии уведомлений объединяются в следующий проход event loop; снимок заменяется целиком, без `await` внутри построения. Чтение `snapshot` после уже полученного уведомления завершает отложенную перестройку синхронно. При ошибке обновления каталог очищается и ошибка передаётся вызывающему коду, вместо использования потенциально устаревшего exposure. Ранее сохранённый снимок остаётся историческим: потребитель должен брать актуальный снимок на запрос, а HA — повторно проверять цели при выполнении.

`async_should_expose` в этой версии HA может сохранять вычисленные defaults в registry/storage; это штатная семантика, не самовольное включение exposure. Глобальный переключатель «показывать новые сущности» не уведомляет exposure listener и не отменяет уже сохранённые решения для существующих сущностей; новые states проверяются по актуальным настройкам. Собственный monkey patch или периодический polling не используется.

`tests/test_catalog.py` использует настоящие entity/device/area registries и инициализированный `ExposedEntities`, без подмены правил именования или exposure. Проверены динамические aliases/имена, коллизии, exposure, настройки новых сущностей, события state, наследование комнаты от parent device, неизменяемость поколений, объединение обновлений и teardown. Lifecycle-проверки в `tests/test_ha_runtime.py` дополнительно подтверждают rollback неуспешного/отменённого setup и сохранение каталога при неуспешном unload платформы. После установки `a87d444` пользователь подтвердил совместную проверку каталога и морфологии в своём HA («Проверил. Все ок»); отдельный протокол сценариев не предоставлен.

## Ограничения

- Sentence triggers могут обработать исходный текст до выбранного агента независимо от выключенного предпочтения локальных команд. Полный перехват pipeline не входит в выбранную архитектуру.
- Выбор fallback в каркасе ограничен conversation entity ID. Старые агенты, зарегистрированные только по config entry ID без entity, пока не поддерживаются.
- Каркас объявляет только русский язык согласно границам MVP, даже если fallback поддерживает другие языки.
- Прямая обработка через `conversation.process` пройдёт через Morpholizer только при явном выборе его агента.
- Follow-up зависит от корректного `continue_conversation` выбранного агента; по пунктуации ответа он не определяется.
- Внутренняя история содержит нормализованный текст текущей реплики. Исходный `ConversationInput`/trace остаётся неизменным; подписчик, уже получивший событие исходного user-сообщения, не получает отдельного события его замены. Поэтому live-представление исходной реплики и последующее чтение внутренней истории могут отличаться.
- Защита от прямого self-fallback не заменяет защиту от циклов, создаваемых сторонними агентами-маршрутизаторами. Такие цепочки не являются поддерживаемой конфигурацией MVP.

## Дальнейшее разделение модулей

`conversation.py` остаётся адаптером HA и маршрутизатором. Каталог реализован в `catalog.py`, независимая от HA нормализация — в `normalizer.py` и `morphology.py`. `matching.py` для fuzzy matching появится в 006; пустая заглушка заранее не создаётся.

## Морфологическая нормализация (задача 005)

`Morphology` использует `pymorphy3==2.0.6` и `pymorphy3-dicts-ru==2.4.417150.4580142`; совместная установка и разбор проверены на Python 3.14.4 и HA 2026.11.1. Анализатор создаётся через `hass.async_add_executor_job` при setup conversation-платформы. На запросах подготовка имён и обработка текста также выполняются в executor. Кэш 4096 слов принадлежит экземпляру и не удерживает старые анализаторы глобально; подготовленные кандидаты хранятся только для последнего набора имён. Разбор защищён lock, подготовленные поколения неизменяемы.

Чистый `Normalizer.normalize(text, candidates)` возвращает исходный/итоговый текст и структурированные решения с offsets, исходным фрагментом, кандидатами, методом и причиной. Токенизация сохраняет позиции; изменения применяются к найденным spans, не ко всему запросу. Точные aliases имеют приоритет. Для остальных используются пересечения известных словарных лемм с совместимой частью речи и score не ниже 0.05. Это порог осторожного отбора, а не гарантия вероятности правильного действия. Правдоподобный глагольный разбор изменяемого токена заставляет отказаться от замены. Латиница и числовые токены в составе названия должны совпасть буквально; числительные не склоняются.

Для сравнения учитываются регистр и `ё/е`, структура внутренней пунктуации сохраняется. Подставляется именно существующее имя/alias, а не леммы. Несколько жизнеспособных кандидатов, разные возможные выходные aliases и неразрешимые пересечения оставляют соответствующий фрагмент без замены; отказ максимального фрагмента не превращается в замену его короткой части. Пустые решения означают отсутствие подходящих фрагментов; отдельная диагностика отказа есть для неоднозначных кандидатов, пересечений и правдоподобного глагольного разбора. Полный текст запросов и объяснения не логируются.

Каталог может обновиться во время executor job. Результат применяется только к тому же поколению snapshot; при изменении выполняется одна повторная попытка, затем сохраняется исходный текст. Явное продолжение LLM целиком обходит нормализатор, а состояние маршрута потребляется до первого `await`, включая отмену анализа.

Чтобы HA не добавил второе user-сообщение при вложенном `async_converse` с другим текстом, текущий `UserContent` заменяется через `dataclasses.replace` до локального этапа/делегирования. Сохраняются attachments и время создания; исходный объект запроса не мутируется. Возвращаемые поля результата fallback и контекст пользователя не подменяются.

Скрипт `scripts/benchmark_normalizer.py` воспроизводит синтетический замер. На текущем Linux/Python 3.14.4: холодная загрузка около 48 мс, RSS анализатора около +23 MiB; при 1000 именах первая обработка около 18 мс, прогретая медиана около 12 мс и p95 около 13 мс (100 повторов). Это измерение данного окружения, не гарантия для устройства HA. Скрипт использует только pure-модули без загрузки HA.
